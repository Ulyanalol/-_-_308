 Техническое задание
 Проект: «Система учёта заявок технической поддержки»

 1. Назначение системы

Система учёта заявок технической поддержки предназначена для регистрации, обработки и контроля обращений пользователей, связанных с неисправностями компьютеров, проблемами с интернетом, принтерами и программным обеспечением.

Система позволит пользователям создавать заявки и отслеживать их состояние. Операторы смогут распределять заявки между исполнителями, а исполнители — работать над решением технических проблем и изменять статусы обращений.

 2. Проблема, которую решает система

При отсутствии единой системы обращения пользователей могут теряться, обрабатываться с задержками или оставаться без назначенного исполнителя. Также может быть сложно узнать, на каком этапе находится решение проблемы.

Разрабатываемая система позволит хранить обращения в одном месте, контролировать их выполнение и сохранять историю изменений.

 3. Пользователи и роли

1. Администратор — управляет учётными записями пользователей и настройками системы.
2. Оператор — просматривает поступившие заявки, проверяет их и назначает исполнителей.
3. Исполнитель — рассматривает назначенные заявки, устраняет проблемы и обновляет их статусы.
4. Заявитель — создаёт обращения, просматривает свои заявки и получает информацию об их выполнении.

 4. Функциональные требования

- FR-01. Система должна предоставлять пользователям возможность входа в учётную запись.
- FR-02. Система должна позволять заявителю создавать новую заявку.
- FR-03. Система должна сохранять тему и описание каждой заявки.
- FR-04. Система должна автоматически присваивать каждой заявке уникальный номер.
- FR-05. Система должна предоставлять возможность выбора категории заявки.
- FR-06. Система должна позволять оператору назначать исполнителя для заявки.
- FR-07. Система должна позволять уполномоченным пользователям изменять статус заявки.
- FR-08. Система должна отображать список заявок в соответствии с правами пользователя.
- FR-09. Система должна предоставлять поиск заявок по номеру или теме.
- FR-10. Система должна позволять фильтровать заявки по статусу и категории.
- FR-11. Система должна позволять пользователям добавлять комментарии к заявкам в соответствии с их правами.
- FR-12. Система должна сохранять историю изменений заявок.

 5. Нефункциональные требования

- NFR-01. Интерфейс системы должен быть понятным и удобным для пользователей.
- NFR-02. Система должна сохранять данные заявок после завершения работы программы.
- NFR-03. Система должна ограничивать доступ к функциям в соответствии с ролью пользователя.
- NFR-04. Система должна сообщать пользователю об ошибках при некорректном вводе данных.
- NFR-05. Структура программы должна позволять добавлять новые функции без полной переработки системы.

 6. Основные категории заявок

1. Неисправность компьютера.
2. Проблемы с интернетом.
3. Неисправность принтера.
4. Проблемы с программным обеспечением.

 7. Статусы заявок

В системе используются четыре статуса:

- Новая — заявка зарегистрирована.
- В работе — исполнитель занимается решением проблемы.
- Выполнена — исполнитель завершил работу.
- Закрыта — обработка заявки окончательно завершена.

 8. Основные сущности системы

1. Пользователь (User) — сведения об учётной записи, имя, логин и роль.
2. Заявка (Request) — номер, тема, описание, дата создания, категория, статус и исполнитель.
3. Категория (Category) — название и описание категории обращения.
4. Статус (Status) — название и описание состояния заявки.
5. Комментарий (Comment) — текст сообщения, автор и дата добавления.
6. История заявки (RequestHistory) — сведения об изменениях заявки, автор изменения и дата события.

Исполнитель и заявитель являются пользователями с соответствующими ролями, поэтому отдельные сущности для них не требуются.

 9. Основные сценарии использования

Сценарий 1. Создание заявки

1. Заявитель входит в систему.
2. Открывает форму создания заявки.
3. Указывает тему, описание и категорию проблемы.
4. Отправляет заявку.
5. Система сохраняет заявку и присваивает ей уникальный номер.
6. Заявка получает статус «Новая».

Сценарий 2. Назначение исполнителя

1. Оператор входит в систему.
2. Открывает список новых заявок.
3. Выбирает заявку.
4. Назначает исполнителя.
5. Система сохраняет назначение.

Сценарий 3. Выполнение заявки

1. Исполнитель открывает назначенную ему заявку.
2. Изучает описание проблемы.
3. Начинает работу и переводит заявку в статус «В работе».
4. После завершения работы переводит её в статус «Выполнена».
5. Система сохраняет изменения.

Сценарий 4. Просмотр результата

1. Заявитель входит в систему.
2. Открывает список своих заявок.
3. Выбирает нужную заявку.
4. Просматривает её статус и комментарии.

 10. Критерии приёмки

Система считается соответствующей основным требованиям, если:

1. Пользователь может войти в систему.
2. Заявитель может создать заявку.
3. Каждая заявка получает уникальный номер.
4. Заявке можно назначить одну из предусмотренных категорий.
5. Оператор может назначить исполнителя.
6. Статус заявки можно изменить в соответствии с правами пользователя.
7. Пользователь может просматривать доступные ему заявки.
8. Работают поиск и фильтрация заявок.
9. Пользователи могут добавлять комментарии в соответствии со своими правами.
10. Изменения заявок сохраняются.

 11. Технологии разработки

- Язык программирования: Python 3.12 или новее.
- Система контроля версий: Git.
- Удалённый репозиторий: GitHub или GitLab.
- Для хранения данных на этапе реализации планируется использовать SQLite.

 12. Ограничения и уточнения

Система предназначена для учёта технических обращений. Она не выполняет автоматическую диагностику неисправностей оборудования. Решение проблемы выполняет назначенный специалист.

Порядок закрытия заявки и права на изменение статусов должны быть уточнены при проектировании системы.
